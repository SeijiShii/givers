# 悪用の定義・禁止行為と対応方針

GIVErS における「悪用」の定義、禁止行為の類型、マネーロンダリング対策、および検知・対応フローを整理する。利用規約の禁止行為条項と、ホストの利用停止判断の根拠となる基準のたたき台である。弁護士確認を経て利用規約に反映する前提。

**最終更新**: 2026-03

---

## 1. 悪用（禁止行為）の定義

「悪用」とは、以下の類型に該当する行為またはその疑いのある行為をいう。利用者（寄付者・プロジェクトオーナーを問わず）がこれらに該当する利用を行った場合、ホストは利用停止・プロジェクト凍結・削除等の対応を行うことができる。

### 1.1 詐欺的プロジェクト

寄付金を騙し取る意図、または本来の目的外に使用する意図をもったプロジェクトの作成・運営。

**具体例**:
- 虚偽の説明（存在しない活動・架空の団体・偽の実績等）でプロジェクトを作成し、寄付を募る
- 実在する他者・団体を騙ってプロジェクトを作成する（なりすまし）
- 集めた寄付金を説明した用途と著しく異なる目的に使用する
- 同一内容のプロジェクトを複数作成し、同じ活動に対して重複して寄付を募る

### 1.2 マネーロンダリング・犯罪収益移転

犯罪によって得た収益の出所を隠蔽する目的、または犯罪収益を正当な資金に見せかける目的で、プラットフォームの寄付機能を利用する行為。

**具体例**:
- 犯罪収益をカード決済で寄付し、受領者の銀行口座から引き出すことで資金の出所を偽装する
- 自己取引 — 自身が管理するプロジェクトに自ら寄付し、資金を移動させる（後述 §3.3）
- 寄付と返金を反復して資金の追跡を困難にする（round-tripping）
- 第三者の名義・アカウントを利用して寄付を行い、資金の流れを不透明にする

### 1.3 盗難カード・不正決済

窃取・不正取得されたクレジットカード情報を用いた寄付。

**具体例**:
- 盗難カード・漏洩カード情報を用いた寄付
- 他人のカードを無断で使用した寄付
- カードテスティング（少額の寄付を大量に行い、カードの有効性を確認する行為）
- 異常な頻度・金額のチャージバック発生

### 1.4 テロ資金供与・制裁対象者

テロ組織への資金供与、または国内外の経済制裁の対象となる個人・団体との取引。

**具体例**:
- テロ組織・テロリストとして指定された個人・団体が運営するプロジェクトへの寄付、またはそれらが受領者となるプロジェクトの作成
- 外国為替及び外国貿易法（外為法）・国連安全保障理事会決議等に基づく経済制裁の対象者が関与する取引

### 1.5 反社会的勢力との関与

暴力団、暴力団員、暴力団準構成員、暴力団関係企業、総会屋等、社会運動等標ぼうゴロ、特殊知能暴力集団等（以下「反社会的勢力」）が利用者として関与する行為。

**具体例**:
- 反社会的勢力がプロジェクトオーナーとしてプラットフォームを利用する
- 反社会的勢力の活動資金を調達する目的でプロジェクトを作成する
- 反社会的勢力であることを隠して利用する

### 1.6 寄付メッセージの悪用

寄付に付随するメッセージ機能を、本来の目的（応援・感謝の表明）以外の有害な用途に使用する行為。

**具体例**:
- 脅迫・恐喝を含むメッセージの送信
- ハラスメント・誹謗中傷・差別的表現を含むメッセージの送信
- 広告・スパムリンクの送信
- 違法な内容（児童ポルノ・薬物取引の勧誘等）を含むメッセージの送信

### 1.7 システムの技術的悪用

プラットフォームの技術的仕組みを不正に利用・攻撃する行為。

**具体例**:
- レートリミットの回避（IP 偽装・分散アクセス等）
- Webhook の偽装・リプレイ攻撃
- API の脆弱性を突く不正アクセス
- 自動化ツール・ボットによるスパム的な寄付の生成
- 他のユーザーのアカウントへの不正アクセス

### 1.8 法令違反コンテンツ

法令に違反する商品・サービス・活動の資金調達、または法令に違反するコンテンツの掲載。

**具体例**:
- 違法な商品・サービス（薬物、武器等）の製造・販売・配布のための資金調達
- 著作権・商標権等の知的財産権を侵害するコンテンツの掲載
- わいせつ物・児童ポルノ等の法令で禁止されたコンテンツの掲載

### 1.9 税額控除の虚偽表明

認定NPO法人等の税額控除対象団体でないにもかかわらず、「税額控除対象」と虚偽の表明を行う行為。

**具体例**:
- 認定NPO法人等の認定を受けていないにもかかわらず、プロジェクト上で「税額控除対象」と表示する
- 失効・取消済みの認定番号を使用する
- 他団体の認定番号を流用する

## 2. 判断の原則

### 2.1 合理的根拠に基づく判断

ホストの利用停止・凍結判断は、以下の原則に基づく：

- **客観的な事実・データ**（通報内容、寄付パターン、チャージバック記録等）に基づくこと
- **判断の根拠と経緯を記録**すること（§5 参照）
- **恣意的な判断を避ける**ため、本文書の類型と後述の対応フローに沿って判断すること

### 2.2 疑いの程度と対応の比例

- **確証がない段階**では利用停止ではなく調査・監視を優先する
- 対応の重さ（警告 → 利用停止 → 法的対応）は、悪用の重大性・証拠の確度に比例させる
- **急を要する場合**（盗難カードの大量使用、明白な詐欺等）は、先に利用停止を行い、事後に調査・記録を行うことを妨げない

## 3. マネーロンダリング対策（AML）

### 3.1 プラットフォームの立場

GIVErS は寄付金の仲立ちをせず、Stripe Connect を通じて寄付者からプロジェクトオーナーに直接入金する。プラットフォームは**資金移動業者・金融仲介者ではない**。ただし、決済導線を提供するサービスとして、マネーロンダリングに利用されるリスクを認識し、合理的な対策を講じる。

### 3.2 既存の対策（実装済み）

| 対策 | 詳細 |
|------|------|
| **受領者の本人確認（Stripe KYC）** | プロジェクトオーナーは Stripe Connect オンボーディングで身分証提出・銀行口座登録を完了。匿名での受領は不可。 |
| **寄付者のカード認証（Stripe）** | 寄付者はカード発行元の本人確認に依存。Stripe Checkout が 3D セキュア等を処理。 |
| **レートリミット** | 決済エンドポイントに IP ベースで 10 回/分の制限。Checkout Session の乱造を防止。 |
| **寄付履歴の永続保存** | すべての寄付記録（金額・日時・donor_type・donor_id・stripe_payment_id 等）を永続保存。AML 記録保持の役割も果たす。 |
| **利用停止時のサブスク解約** | 悪用者のアカウント停止と同時に、紐づく定期寄付を Stripe 上で解約。継続的な資金流入を遮断。 |
| **返金機能** | ホスト・オーナーが Stripe API 経由で個別の寄付に全額返金を実行可能。不正な寄付の資金を取り消せる。 |

### 3.3 将来の検討事項（未実装）

以下は、サービスの規模拡大に応じて段階的に検討・実装する対策である。

#### 3.3.1 自己取引の検知

同一ユーザーが「プロジェクトオーナー」かつ「寄付者」となるパターンを検知する。

- **検知方法**: 寄付の `donor_id`（user）とプロジェクトの `owner_id` を照合
- **対応**: 自動フラグ → ホストが確認 → 合理的な理由がなければ利用停止
- **留意**: テスト寄付（少額・自プロジェクト）は正当な用途の場合があるため、金額・頻度の閾値を設定

#### 3.3.2 異常パターンの監視

以下のパターンを定期的に監視するダッシュボード・アラートの実装を検討する。

| パターン | 指標 |
|----------|------|
| **高頻度寄付** | 同一 donor から短期間（例: 24時間以内）に N 回以上の寄付 |
| **高額寄付** | 1 回あたり・1 日あたりの寄付金額が閾値を超過 |
| **反復的寄付→返金** | 同一 donor-project 間で寄付→全額返金が N 回以上反復（round-tripping） |
| **同一 donor→同一 project 集中** | 特定の donor-project ペアに異常な集中 |
| **チャージバック率** | プロジェクト単位・プラットフォーム全体のチャージバック率が閾値を超過 |

- 閾値は運用開始後のデータに基づいて調整する
- Stripe Radar の活用も併せて検討する

#### 3.3.3 寄付金額の上限設定

- 1 回あたり・1 日あたり・1 ヶ月あたりの寄付金額上限の設定を検討する
- Stripe 側の制限に加え、プラットフォーム独自の上限を設けるか、弁護士・Stripe の助言に基づいて判断する

#### 3.3.4 疑わしい取引の報告

- 犯罪収益移転防止法上、プラットフォームが「特定事業者」に該当するかどうかを弁護士に確認する
- 該当する場合は疑わしい取引の届出義務（SAR）が生じうる
- 該当しない場合でも、犯罪の疑いがある場合は自主的に法執行機関へ通報する方針とする

## 4. 対応フロー（詳細手順）

### 4.1 検知・通報の受付

悪用の検知・通報は以下の経路から行われる。

| 経路 | 内容 |
|------|------|
| **利用者からの通報** | お問い合わせフォーム・メール等でホストに報告 |
| **Stripe からの通知** | チャージバック通知、Radar によるフラグ、アカウント審査結果等 |
| **ホストによる発見** | 管理画面でのデータ確認中に異常を発見 |
| **システムアラート**（将来） | §3.3.2 の異常パターン監視による自動検知 |

**受付時の記録項目**:
- 通報日時
- 通報経路（利用者通報 / Stripe 通知 / ホスト発見 / システムアラート）
- 対象（ユーザーID / プロジェクトID / 寄付ID）
- 通報内容の要約

### 4.2 調査

受付後、ホストは以下の項目を確認する。

#### 調査項目チェックリスト

- [ ] **対象ユーザーの基本情報**: アカウント作成日、認証プロバイダ、ステータス
- [ ] **対象プロジェクトの情報**: 説明内容の妥当性、オーナーの Stripe Connect ステータス
- [ ] **寄付履歴の確認**: 金額・頻度・パターンに異常がないか（管理画面 or 開示用データ出力機能を使用）
- [ ] **Stripe ダッシュボードの確認**: チャージバック有無、Radar のフラグ、決済の詳細
- [ ] **自己取引の有無**: donor_id と project owner_id の一致確認
- [ ] **類似通報の有無**: 同一ユーザー・プロジェクトに対する過去の通報記録
- [ ] **外部情報の確認**（必要に応じて）: 団体の実在性、公的データベースとの照合

### 4.3 判断

調査結果に基づき、以下の判断基準に沿って対応を決定する。

| 判断 | 基準 | 対応 |
|------|------|------|
| **悪用なし** | 調査の結果、禁止行為に該当する事実が認められない | 記録のみ（調査記録を保存） |
| **グレー（要監視）** | 疑わしいが確証がない。パターンが異常だが説明がつく可能性もある | 監視対象として記録。一定期間の経過観察。必要に応じて利用者へ確認連絡 |
| **軽度の違反** | 禁止行為に該当するが、意図的な悪用とは断定できない。初回。影響が限定的 | 警告 + 是正要求（メール等で通知） |
| **重度の違反** | 意図的な悪用が明白。反復的。影響が大きい。警告後の再犯 | **利用停止**（+ 紐づくサブスクの解約）。必要に応じて**返金の実施** |
| **犯罪の疑い** | マネーロンダリング、詐欺、テロ資金供与等の犯罪の疑いがある | **即時利用停止** + **弁護士相談** + 弁護士助言に基づき**法執行機関への通報** |

### 4.4 対応の実施

#### 4.4.1 警告

- 対象ユーザーにメール等で通知する
- 通知内容: 該当する禁止行為の類型、是正要求の内容、期限、是正しない場合の措置
- 通知日時・内容を記録する

#### 4.4.2 利用停止

- 管理画面からアカウントを利用停止にする
- 利用停止と同時に、紐づく定期寄付（Stripe サブスク）を解約する（実装済み）
- 対象ユーザーのプロジェクトを凍結する
- 不正な寄付に対して返金の要否を判断する
  - 盗難カードの場合: Stripe のチャージバックプロセスに委ねる
  - 詐欺的プロジェクトの場合: 当該プロジェクトへの寄付者に対する返金を検討する
- 対象ユーザーにメール等で利用停止の通知を行う
  - 通知内容: 利用停止の事実、該当する禁止行為の類型、異議申し立ての方法

#### 4.4.3 法的対応

- 弁護士に相談し、助言に基づいて対応する
- 法執行機関への通報が必要な場合:
  - 開示用データ出力機能（実装済み）で対象データを JSON 出力する
  - 弁護士の助言に従い、適切な機関（警察・金融庁等）に通報する
- Stripe への報告: Stripe サポートに不正利用の報告を行う

### 4.5 異議申し立て

利用停止を受けたユーザーが異議を申し立てる場合の対応：

- お問い合わせフォーム・メールで異議を受け付ける
- ホストが異議内容を確認し、調査記録と照合する
- 誤認であった場合は利用停止を解除し、記録を更新する
- 判断が妥当であった場合は、その旨を理由とともに通知する

## 5. 記録の管理

### 5.1 記録すべき項目

すべての通報・調査・判断・対応について、以下を記録する。

| 項目 | 内容 |
|------|------|
| **案件 ID** | 通報・発見ごとに一意の識別子を付与 |
| **通報日時** | 通報または発見の日時 |
| **通報経路** | 利用者通報 / Stripe 通知 / ホスト発見 / システムアラート |
| **対象** | ユーザーID / プロジェクトID / 寄付ID |
| **類型** | §1 のどの禁止行為に該当するか |
| **調査内容** | 確認した事項と結果のサマリー |
| **判断** | 悪用なし / グレー / 軽度 / 重度 / 犯罪の疑い |
| **対応内容** | 記録のみ / 警告 / 利用停止 / 法的対応 |
| **対応日時** | 対応を実施した日時 |
| **対応者** | 判断・対応を行ったホスト |
| **異議申し立て** | 有無、内容、結果 |

### 5.2 記録方法

- 初期段階ではスプレッドシート・テキストファイル等で管理する
- 案件数の増加に応じて、管理画面内での記録機能の実装を検討する

### 5.3 保存期間

- 通報・調査・対応の記録は**最低 5 年間**保存する（犯罪収益移転防止法の取引記録保存期間を参考）
- 法的紛争が係属中の場合は、解決まで保存する

## 6. 弁護士確認が必要な論点

| 論点 | 内容 |
|------|------|
| **禁止行為の定義** | §1 の類型・具体例が利用規約の禁止行為条項として十分か。過不足・表現の修正。 |
| **利用停止の手続き** | §4 の対応フロー・異議申し立てプロセスが、恣意性・不当停止の主張に対する抗弁として機能するか。 |
| **マネロン規制上の位置づけ** | プラットフォームが犯罪収益移転防止法上の「特定事業者」に該当するか。Stripe への KYC 委任で法的に十分か。 |
| **疑わしい取引の届出** | SAR（疑わしい取引の届出）の義務が生じうるか。自主的な通報の方法と留意点。 |
| **反社条項** | 反社会的勢力の排除条項の文言が利用規約として十分か。 |
| **金額上限** | プラットフォーム独自の寄付金額上限を設定する法的根拠・義務の有無。 |
